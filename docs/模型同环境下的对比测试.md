# 相同 RuntimePolicy 下的 Provider / 模型对比报告

测试日期：2026-08-01

## 结论摘要

本轮使用同一个节点 Profile、同一个 `coding-default` RuntimePolicy，只由测试
Runner 覆盖 `provider_id`。共完成两组单次受控测试：

- 诊断基准：23 个文本/编码 Provider 全部实际发起请求，10 个完整通过。
- 真实改码基准：从上述矩阵选取 12 个代表 Provider，0 个完整通过。

当前 `modelProvider.json` 共 36 个 Provider。诊断矩阵覆盖了其中 23 个可执行通用
文本/编码任务的 Provider；其余 13 个是图像生成、视频、音频、视觉理解、3D、
抠图等媒体专用路径，不具备与同一聊天编码 Profile 可比的输出合同，因此没有用
文本 RuntimePolicy 强行调用。被排除的是 `371NanoBanana`、`Agnes_image`、
`Agnes_video`、`BiRefNet_HR_Matting_Local`、`doubao-seedance-2-0-260128`、
`doubao-seedream-4-0-250828`、`doubao-seedream-4-5-251128`、`doubao-seedream-5`、
`doubao-seedream-5-lite`、`doubao_vision`、`hyper3d-rodin-gen2`、`seed_audio` 和
`wan2.2-animate-mix`。其中个别配置同时声明 `chat`，但其实际模型与主要输出仍为
媒体生成，纳入同一文本质量排名会破坏合同一致性。

诊断基准中，只有完整通过五项事实验收的结果参与排名。前三名为：

1. `GPT_53Fast_Official / gpt-5.3-codex-spark`：8.2 秒，5,601 token。
2. `doubao-pro / doubao-seed-2-1-turbo-260628`：11.6 秒，8,549 token。
3. `sonnet-5-krill / claude-sonnet-5`：13.3 秒，1,447 total token；另有
   11,489 cache-write input，不能把 1,447 直接解释为完整计费量。

真实改码基准没有速度冠军。12 个 Provider 均未通过隐藏功能验收；其中 9 个
在统一的 360 秒上限内超时。所有样本显示的 33.3 分只来自未修改的 fixture
原本就能通过 WebUI build，不代表功能完成。这个结果说明当前
`coding-default` 与该局部 UI 改码任务的组合容易触发长工具循环、迟迟不落盘或
实现未命中验收合同，不能据此给模型做真实改码速度排名。

## 受控基准与变量边界

| 项目 | 固定值 |
|---|---|
| Profile | `benchmarks/profiles/provider-comparison.json` |
| Profile SHA-256 | `8e868022eea3e2ecc63e7bc36acef97ba2b6b68a06da373185858d580a34884b` |
| RuntimePolicy | `coding-default` 1.1.0 |
| 有效 Policy SHA-256 | `4a01c9c2fc8459e4f588da0356008f63f2adda8ee9cd33f275d6e48ad67d2cbe` |
| 节点工具 | 仅 `system_tools` |
| Profile thinking | `disabled` |
| Profile reasoning_effort | 空值，由被切换的 Provider 使用自己的配置 |
| 其他能力 | 无 plugin、skill、MCP、web search、remote worker |
| 唯一主动切换项 | Runner 的 `provider_id` |

这里的“只切换 Provider”意味着 Provider 自身的模型、协议类型、网关、
`reasoningEffort`、缓存和 usage 上报方式也随之切换。这些是 Provider 的有效
配置，不是 Profile 或 RuntimePolicy 漂移。因此跨模型数据衡量的是“当前
Provider 整体执行效果”；只有相同模型的多 Provider 对照，才能进一步观察
网关/协议差异。

每个 Runner 的合同都独立记录 Profile、Provider 配置、RuntimePolicy、fixture、
输入与验证器哈希。速度排名要求 `benchmark_status=completed`、全部必选验收、
验证命令与修改路径门禁同时通过。

## 相同模型的 Provider 对照

### `gpt-5.6-sol`

三个 Provider 在诊断任务都 100% 通过：

| Provider | 配置推理强度 | 耗时 | 总 token | 相对 `GPT_Official` |
|---|---|---:|---:|---|
| `krill_gpt_Newest` | xhigh | 46.8s | 25,264 | 快 27.4%，token 少 68.7% |
| `GPT_Official` | high | 64.5s | 80,602 | 基准 |
| `home_gpt` | xhigh | 71.0s | 73,773 | 慢 10.1%，token 少 8.5% |

同一模型相差 1.5 倍耗时、3.2 倍 token，足以证明网关、缓存、协议、服务负载和
Provider 参数会显著影响结果，不能只按模型名归因。改码任务中
`GPT_Official` 完成但未验收，`krill_gpt_Newest` 超时，差异仍然存在，但由于
双方都未完整通过，不能做胜负判断。

### `grok-4.5`

`Grok_krill` 完整通过诊断；`Grok_Vanyo` 在第二回合前因
`previous_response_id is only supported on Responses WebSocket v2` 返回 HTTP 400。
这是一项 Provider 协议集成差异，不是同名模型的能力差异。

### Kimi 路径

`Kimi_CodingPlan / kimi-k2.7-code` 以 18.7 秒、6,069 token 完整通过诊断；
`Kimi_Newest / kimi-k3` 为 90 分、172.8 秒；`Kimi-K3-AgentPlan / kimi-k3`
为 60 分、211.3 秒。后二者还缺失 usage。当前配置下 CodingPlan 路径明显更适合
这项诊断，但 K3 的两个结果同时包含不同 Provider 适配层，不能直接归因于模型本体。

## 决策建议

1. 诊断/说明型任务的当前首选梯队是 `GPT_53Fast_Official`、`doubao-pro`、
   `sonnet-5-krill`、`Kimi_CodingPlan`；必须先满足事实验收，再看时延和 token。
2. 不应根据本轮给真实改码 Provider 排名。应先解决或调整 `coding-default` 在局部
   UI 任务中的工具循环/落盘节奏，再按同一合同至少重复三次。
3. 局部、边界清晰的 UI 改码可以另建统一的 `coding-fast` Provider 矩阵；历史
   同任务中该 Policy 曾有完整通过结果，但由于 Policy 与 Profile 条件不同，不能
   混入本轮排名。
4. Provider 上线门禁应同时覆盖模型质量与接入完整性：鉴权、Responses 多轮协议、
   usage 完整性、超时取消和缓存计量必须分别判定。
5. 下一轮至少三次重复，报告中使用完成率、通过样本耗时中位数、token 中位数及
   P95；任一轮未完整验收的 Provider 不进入速度冠军比较。

## 解读限制

- 当前每个 Provider 每项任务只有一次样本，能验证合同和发现大差异，不能估计方差。
- token 只在 Provider 正确返回 usage 时可比较；`n/a` 不是零消耗，`≥` 是分项下界。
- 部分 Provider 的 cache-write input 不计入 total，成本必须按各自计费合同重算。
- 本报告比较的是当前 Provider 整体执行路径，不声称得到与网关无关的纯模型排名。
- 诊断任务和改码任务的 fixture revision 不同，但同一任务内所有 Provider 的
  revision、Profile、RuntimePolicy、输入和验收完全一致。
